## Product thesis

DIS should describe not only a domain and its intended transformation, but also how an implementation proves that the transformation works.

The conceptual chain is:

1. `ValueEngineeringProfile` records why the transformation matters.
2. `DossierComparison` records what changes between discovery and design.
3. `EvaluationSuite` records how success will be proven.
4. `EvaluationReceipt` records what was observed and whether promotion gates passed.

A Dossier is expected to live in a Git repository. Git provides durable history, feature branches, review, approval, release tags, and GitOps promotion. A collaborative design session may maintain a live conflict-free editing layer, but protected Git history remains the canonical governance layer.

The public DIS specification defines portable semantics and conformance. The private Dossier Studio product supplies collaboration, compilation, provider adapters, evaluation execution, evidence custody, and enterprise GitOps workflow.

## Proposed v1.7 scope

Version 1.7 should remain additive and backward-compatible. Existing v1.6 dossiers must continue to validate without evaluation constructs. Requiring evaluations or changing existing required fields would be a DIS 2.0 concern.

### EvaluationSuite

`EvaluationSuite` is a versioned, vendor-neutral declaration of the scenarios, evidence, evaluators, and gates used to determine whether a design or deployment meets its intended outcomes.

Candidate top-level properties:

- `suiteId`, `name`, `description`, and `version`
- `scopeRefs` identifying dossiers, triplets, functions, entities, modes, or value metrics under evaluation
- `scenarios` containing deterministic or generated interaction cases
- `evaluators` describing rules, models, humans, or external evaluation services
- `evidenceRequirements` declaring the minimum evidence needed for a valid verdict
- `aggregationPolicy` describing how repetitions and evaluator results combine
- `gatePolicy` defining pass thresholds, critical failures, and promotion behavior
- `valueMetricBindings` connecting technical outcomes back to `ValueEngineeringProfile.metrics`
- standard DIS metadata such as `appliedTags`, `attributes`, `primaryKey`, and `foreignKeys`

Each scenario should be able to express:

- modality or channel, including voice, chat, API, and multimodal interactions
- initial state, inputs, fixtures, and deterministic seed where applicable
- expected behaviors and explicitly prohibited behaviors
- repetitions, concurrency, timing constraints, and termination conditions
- required evidence such as messages, transcripts, recordings, tool traces, events, and latency measurements
- applicable privacy classification and retention requirements

Evaluator types should remain extensible. Initial standard categories may include rule-based, semantic, behavioral, acoustic, performance, safety, business-value, human, and external evaluators. A transcript evaluator and an audio evaluator are separate sources of evidence; a passing transcript score must not erase a critical acoustic failure.

### AdapterBinding

`AdapterBinding` describes the declared capability boundary between an evaluation suite and a target system. It must describe capabilities without embedding a provider's private configuration model in DIS.

Candidate properties:

- `bindingId`, `name`, and `targetRef`
- `interfaceProtocol`, with MCP as the preferred uniform tool boundary
- `capabilityManifest` for control, interaction, and evidence operations
- supported modalities, environments, and fidelity levels
- adapter implementation name and version
- `configurationRef` and `secretRef`; secret values are never valid schema content
- declared limitations, manual steps, and unsupported capabilities

An adapter may be implemented over a public API, SDK, internal management API, SIP or PSTN, browser automation, an iframe, or a manual procedure. These mechanisms are provider-specific implementation details. The capability declaration is portable.

The initial MCP capability families are:

- control: inspect, plan, compile, apply, deploy, promote, and roll back
- interaction: start, send, await, and end
- evidence: messages, transcript, recording, events, tool traces, and metrics

### EvaluationReceipt

`EvaluationReceipt` is an immutable record of one evaluation execution. It is evidence about a particular source revision and deployed artifact, not mutable design intent.

Candidate properties:

- `receiptId`, `suiteId`, `runId`, and timestamps
- Dossier repository identity and commit SHA
- compiled artifact digest
- target binding, deployment, and environment identity
- adapter and evaluator versions
- scenario attempts, scores, verdicts, and critical failures
- evidence references and content hashes
- aggregation result and promotion decision
- human overrides, actor identity, reason, and time
- optional signatures or attestations

Receipts should normally be stored as build artifacts or in an evidence store, with a small manifest committed only when policy requires it. Repeated evaluation runs should not constantly rewrite the source Dossier.

## Dossier integration

The v1.7 `DISDossier` may add optional collections under both `dossierSpecificDefinitions` and `referencedConstructs`:

- `evaluationSuites`
- `adapterBindings`

An `EvaluationReceipt` should be independently addressable and reference the source Dossier revision. Embedding receipts directly in a source Dossier is not the default because results are append-only runtime evidence.

The proposed repository convention is:

```text
dossier.yaml
evaluation/
  regression-suite.yaml
targets/
  candidate-environment.yaml
receipts/
  <run-id>/
    receipt.yaml
    evidence-manifest.yaml
```

The names are a workspace convention, not required schema paths.

## Compile and promotion lifecycle

The intended lifecycle is:

```text
Dossier
  -> validate
  -> compile through a target adapter
  -> deploy to a candidate environment
  -> execute EvaluationSuite
  -> emit EvaluationReceipt
  -> enforce promotion policy
  -> review, tag, and promote through GitOps
```

The runtime product should preserve provenance across this chain. A verdict without a Dossier commit, compiled artifact digest, adapter version, and evidence identity is incomplete.

## Public specification and private product boundary

The public repository should contain:

- the DIS specification and JSON Schemas
- examples and conformance fixtures
- validation and schema-diff rules
- migration guidance
- a small reference validator sufficient for independent implementation

The private product repository should contain:

- the collaborative Dossier Studio
- enterprise identity, authorization, and repository workspace services
- provider-specific compilers and adapters
- evaluation execution and replay infrastructure
- evaluator models and orchestration
- evidence storage and retention controls
- promotion policy, approvals, audit, and enterprise support

The open specification must remain independently readable and implementable. Commercial value comes from making the standard collaborative, executable, continuously evaluated, governed, and operational at enterprise scale.

## Immediate Dossier Studio proof of concept

The POC is a private architectural workbench for an AI design team and an enterprise buyer. Its single job is to co-create a valid, reviewable Dossier visually and save it into a Git working tree.

### Smallest credible vertical slice

1. Open a local Dossier workspace from a Git worktree.
2. Render a typed canvas with a palette of core DIS constructs.
3. Create and move nodes for Entity, Role, Application, Endpoint, AgenticTriplet, and Function constructs.
4. Connect nodes using schema-aware relationships.
5. Edit the selected construct in an inspector generated from its JSON Schema.
6. Show validation problems directly on the affected node and field.
7. Serialize deterministic YAML or JSON without destroying unknown fields.
8. Show the resulting Git diff and source commit identity.
9. Include an experimental EvaluationSuite node so the discovery conversation can attach proof requirements to the design.

Concurrent multi-user editing, provider deployment, production evidence collection, and promotion automation are intentionally outside the first vertical slice. The data model and command boundaries should leave room for them.

### Reuse strategy

The POC should reuse the existing Njordr/diagrams Flutter canvas foundation where its canvas, selection, connection, and layout primitives are separable from its current diagram types. DIS becomes a schema-native editor rather than another Mermaid or LikeC4 renderer. The source of truth is the Dossier, not generated diagram text.

### Visual direction

The workbench should feel like a technical tracing table rather than a generic SaaS dashboard.

The values below are exploratory product-direction notes, not production token authority. An implementation inside an existing Ravenhelm product must use that repository's accepted design-token evidence until a separately approved Dossier Studio design contract supersedes it.

- Palette: mineral paper `#E8EEF2`, graphite `#1F2A30`, blueprint `#2B5B71`, oxblood `#7B2948`, signal amber `#CE7A25`, and instrument white `#F8FBFC`.
- Typography: a condensed technical face for construct titles, a highly readable sans for prose and controls, and a mono face for identifiers and provenance.
- Layout: construct palette on the left, expansive typed canvas in the center, schema inspector on the right, and a compact provenance/diff rail along the bottom.
- Signature element: an engineering-drawing cartouche that continuously shows Dossier identity, branch, commit, schema version, validation state, and compile state.
- Motion: one purposeful compile transition that traces affected graph paths; routine manipulation should remain quiet and immediate.

The visual risk is the cartouche: it makes Git and schema provenance part of the design language instead of hiding them in settings. This is specific to a tool whose canvas is expected to compile and enter enterprise GitOps.

## Decisions still required before schema implementation

- Whether `AdapterBinding` belongs in the core DIS schema or a companion execution profile.
- Whether `EvaluationSuite` scopes constructs through a generic typed reference or explicit per-construct ID arrays.
- Which evaluator categories and evidence types are normative enums versus extensible strings.
- Whether `EvaluationReceipt` is a core construct, a companion assurance schema, or both through a minimal core envelope.
- How receipt signatures, privacy classifications, and retention policies integrate with existing DIS governance constructs.
- Whether YAML is normative, supported through a canonical JSON mapping, or only a workspace convenience.
- The minimum conformance suite required to call an implementation DIS 1.7 compatible.

## Explicit non-goals for v1.7

- No provider-specific configuration fields in the public core.
- No secrets embedded in a Dossier, adapter binding, or receipt.
- No mandatory evaluation requirement for existing dossiers.
- No assumption that every provider exposes the same interaction or evidence fidelity.
- No coupling of the public specification release to the private tool release.
- No replacement of Git review and approval with ephemeral canvas collaboration state.
